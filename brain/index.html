01 Product overview

The shortlist problem #

GeM publishes thousands of bids. The expensive part is not finding them — it is deciding, quickly and defensibly, which handful deserve a bid team's week.

Tender discovery today is a manual loop: open GeM, page through listings, open PDFs, copy values into a sheet, guess whether the eligibility bar is reachable, and repeat tomorrow. Relevant bids are missed because they close in a few days, and irrelevant ones waste hours because the exclusion only becomes obvious inside the document.

GeM Tender Brain turns that loop into a repeatable scan. A configurable search profile is applied to live (or sample) bids, each survivor gets an explainable score, the top documents are parsed for eligibility signals, and the result is a ranked dashboard plus a shareable sheet — in one run.

Recover the hours

Replace daily paging and spreadsheet copying with one scan that filters, scores and summarises in a single pass.

Protect the focus

Hard filters remove construction, housekeeping, furniture and vehicle work before it ever reaches the bid team.

Surface the risk early

Turnover, experience, OEM and EMD requirements are extracted from the PDF and flagged before a bid is committed.

Positioning. This is a decision-support tool, not a bidding bot. It never submits a bid, never signs a document, and never invents an eligibility claim. Every summary is traceable to a tender field or the tender PDF.

02 Goals

What success looks like #

Measured on a weekly scan cycle, not on lines of code.

Goals

  • One scan, one shortlist. A complete run produces a ranked, readable list without manual copy-paste.
  • Explain every ranking. Each tender shows the exact points added or removed, so a low score can be defended.
  • Filter before enrichment. Cheap rules reject obvious mismatches before any PDF download or AI call.
  • Never miss a closing date. Bids inside the minimum runway are rejected with a visible reason.
  • Degrade gracefully. No API key, no Google account, or a blocked GeM request still leaves a usable run.
  • Stay local by default. Settings and results live on disk; cloud services are optional mirrors.

Non-goals

  • Automated bid submission, DSC signing or portal form filling.
  • Guaranteeing eligibility or legal compliance.
  • Replacing a human review of the tender document.
  • Multi-tenant accounts, roles or billing.
  • Real-time streaming of every new GeM bid.
  • Becoming a CRM for post-award contract management.

06 Requirements

Functional requirements #

P0 requirements are required for a usable run; P1 requirements improve trust and shareability.

IDRequirementAcceptance criteriaPrio
FR-01 Search profile
Categories, keywords, region, states, caps, runway, bid type, score floor, enrichment depth.		 Editable in the UI, validated by Pydantic, persisted to disk, and reused by API and CLI runs. P0
FR-02 Bid acquisition
Live GeM fetch, optional browser fallback, offline sample dataset.		 Every run declares its source. Sample bids are never presented as live, and a fetch failure leaves a readable error. P0
FR-03 Hard filtering
Exclusions, closing window, value caps, EMD cap, bid type, region.		 Rejected tenders never reach scoring or PDF work, and each rejection reason is counted. P0
FR-04 Explainable scoring
Positive signals and risk penalties, shown line by line.		 Every displayed score can be reconstructed from its breakdown; totals never go below zero. P0
FR-05 PDF enrichment
Download cap, text extraction, eligibility signals, re-score.		 Top N tenders are parsed within the size cap; a failed PDF is logged without failing the run. P1
FR-06 Summaries
Groq when available, deterministic rules otherwise.		 Summary source is recorded; no summary asserts eligibility that is not present in the source text. P1
FR-07 Ranked workspace
Dashboard table, detail card, score breakdown, source links.		 Search and filters work without re-running the scan; CSV export matches the visible shortlist. P0
FR-08 Shareable output
Google Sheets mirror and CSV.		 Export is idempotent: reruns overwrite the same tabs instead of duplicating rows. P1
FR-09 Background runs
Threaded execution with pollable progress and history.		 The UI stays responsive; a second concurrent run is refused with HTTP 409. P1
FR-10 Headless operation
CLI run/export commands and a scheduled workflow template.		 A scheduled run produces a saved record and a CSV artifact without the UI. P1

Non-functional baseline. Runs on Windows, macOS and Linux with Python 3.11+. No database. All external calls have timeouts, PDF downloads have a byte cap, and every persisted write is atomic.

07 Filtering

Hard rules, applied in order #

A tender must pass every rule. The first failure is recorded as the rejection reason.

#RuleDefaultRejection label
1Excluded keyword appears in title or categoryconstruction, civil, furniture, vehicle hire, security guard, housekeeping, catering, gardening, plumbing, electrical works, painting, road work, building work, manpower supplyexcluded keyword: …
2Closing too soonFewer than min_days_remaining = 7 daysclosing too soon
3Category relevanceMust match a configured IT or other category/keywordnot relevant to configured categories
4Value cap₹25,00,000 IT · ₹5,00,000 othervalue above limit
5EMD cap₹50,000EMD above limit
6Bid type (only when configured)Product / Service, empty means anybid type mismatch
7Region (only when not All India)Selected region plus preferred statesoutside selected region
8Score floor25 pointsscore below threshold

Why filters run before enrichment

PDF downloads and model calls are the slow, failure-prone parts of a scan. Rejecting obvious mismatches first keeps a typical run in seconds instead of minutes, and keeps request volume low.

Why reasons are counted

Rejection counts reveal a misconfigured profile. If most bids are dropped as “value above limit”, the cap is too tight; if “not relevant” dominates, the keyword list is too narrow.

Exclusions are literal substring matches. “civil” will also reject “civil supplies” unless the keyword is tightened. Review the rejection counts after changing the profile and prefer specific phrases.

Two processes, one virtual environment, no database. The first run works offline.

13 Google Sheets

A readable mirror, not a second source of truth #

Sheets is where stakeholders review. The app remains authoritative for filters and results.

One-time setup

  1. Enable the Sheets API in a Google Cloud project.
  2. Create a service account and download its JSON key.
  3. Share the spreadsheet with the service account as Editor.
  4. Wire up GOOGLE_SERVICE_ACCOUNT_JSON and GOOGLE_SHEET_ID.
  5. Switch on Export to Google Sheets.

What gets written

TabContents

Service account and Sheets API, step by step

Two separate permissions must line up: the API must be enabled in a Google Cloud project, and the spreadsheet must be shared with the service account. A service account is a robot identity with its own email address, so enabling the API alone changes nothing — and neither does sharing alone.

Step 1

Create a Cloud project

Open console.cloud.google.com and create a project, for example gem-tenders. Its project id becomes part of the service-account email.

Step 2

Enable the Sheets API

Go to APIs & Services → Library, search for Google Sheets API and press Enable. Allow about a minute for it to propagate. Enable Google Drive API too only if you want scripts to create spreadsheets; writing to an existing shared sheet needs the Sheets API alone.

Step 3

Create the service account

APIs & Services → Credentials → Create credentials → Service account. Name it gem-sheets and save. No IAM role is required — access comes from the spreadsheet share, not from the project.

Step 4

Download the JSON key

Open the service account and choose Keys → Add key → Create new key → JSON. The file downloads once. Store it as secrets/service-account.json and point GOOGLE_SERVICE_ACCOUNT_JSON at it; the secrets/ pattern is git-ignored.

Step 5

Share the spreadsheet

Open the target sheet, press Share, and add the address from client_email in the key file — it looks like gem-sheets@project-id.iam.gserviceaccount.com. Choose Editor and confirm. Viewer is not enough, because every export clears and rewrites the tabs.

Step 6

Connect the app

Copy the id between /d/ and /edit in the sheet URL into GOOGLE_SHEET_ID or Settings → Google Sheet ID, then switch on Export to Google Sheets. The settings value wins; the environment variable is the fallback.

verify — can the robot open the sheet?
# Run from the project root. A title means API, key and sharing are all correct.
.\.venv\Scripts\python.exe -c "from backend import config; from backend.sheets import _load_client; print('connected to:', _load_client().open_by_key(config.GOOGLE_SHEET_ID).title)"
verify — export the latest saved run
# Writes the Settings and Tenders tabs, then prints a status object.
.\.venv\Scripts\python.exe -m backend.cli export

A healthy export returns {"status": "ok", "rows_written": 25, ...}. Anything else is explained below.

Diagnosing a failed export

MessageMeaningFix
403 SERVICE_DISABLED … sheets.googleapis.comSheets API is off in the project behind the keyEnable it (Step 2), then retry after a minute
403 SERVICE_DISABLED … drive.googleapis.comDrive API is offOnly needed to create files; enable it if you need that
403 The caller does not have permissionThe sheet is not shared with the service accountShare it as Editor with client_email (Step 5)
404 Requested entity was not foundWrong or deleted sheet idRe-copy the id from the sheet URL
invalid_grantKey revoked or rotated, or the clock is wrongGenerate a fresh key and check system time
Quota exceeded … per minuteToo many write requestsExport once per run, not once per tender

Common mix-up: sharing the sheet with your own Gmail address does nothing. The invite must go to the service-account address shown as client_email in the JSON key — a robot identity that can never sign in to the sheet.

Editing the sheet does not change the scan. The Settings tab is a mirror written on export. To change filters, use the app's Settings tab; the next run will overwrite the sheet snapshot.

Export behaviour

  • Idempotent. Each export rewrites the same tabs; rows are not appended, so a rerun never duplicates the shortlist.
  • Non-fatal. A failed export is recorded in RunRecord.errors and the run still completes with local results.
  • Re-exportable. POST /api/export or python -m backend.cli export rebuilds the sheet from a saved run without scanning again.

15 Automation

CLI and scheduled scans #

The same pipeline runs without a browser, which makes it suitable for cron, Task Scheduler and GitHub Actions.

Command line
# Offline demo with a CSV export
python -m backend.cli run --sample --csv artifacts/tenders.csv

# Fastest live run: no PDF parsing, rule-based summaries
python -m backend.cli run --no-pdf --no-ai

# Live run plus Google Sheets mirror
python -m backend.cli run --sheet

# Re-export a stored run
python -m backend.cli export --run-id 20261125T215847-5ccb24

# One-shot entry point for schedulers
python run_once.py

Run flags

FlagEffect

--no-pdfSkip tender document parsing
--no-aiForce rule-based summaries
--sheetEnable Google Sheets export
--pages NOverride page count (1–50)
--csv PATHWrite the shortlist as CSV
--jsonPrint the full run record

GitHub Actions

  1. Copy deploy/github-actions-gem-tenders.yml to .github/workflows/gem-tenders.yml.
  2. Add repository secrets: GROQ_API_KEY, GOOGLE_SERVICE_ACCOUNT_JSON, GOOGLE_SHEET_ID.
  3. Run it manually from the Actions tab, or uncomment the schedule block.
  4. Download the generated CSV from the workflow artifacts.

GitHub-hosted runners have different network egress than your machine. A live GeM run that fails locally may still succeed in CI — or the reverse. Always keep sample mode available for smoke tests.

Scheduling locally

On Windows, create a Task Scheduler job that runs run_once.py with the project's virtual environment. On Linux/macOS, a cron entry such as 0 8 * * 1-5 gives a weekday-morning shortlist before the team starts.

17 Risks

Limits, and how they are handled #

This product depends on a website with no public contract. Design for failure, not for stability.

RiskImpactMitigationSeverity
GeM blocks automated requests No live results. Observed as HTTP 403 from some networks. Optional Playwright session, browser-like headers, sample fallback with a clear source label. High
Undocumented endpoint changes Fields disappear or pagination breaks after a GeM release. Normalisation is isolated in gem_client.py; missing fields degrade to blanks rather than crashing. Medium
Eligibility extraction is heuristic A missed clause could make a tender look safer than it is. Flags are presented as “check this”, never as approval; the source link is always shown. Medium
AI summary drift A model could imply eligibility that the document does not support. Strict prompt, short factual output, rule-based fallback, and no eligibility claims in summaries. Medium
Rate limits and terms of use Aggressive scanning could get the network blocked. Page cap, request timeout, no parallel fetch, and a recommendation to scan at most a few times per day. Low
Credential exposure A leaked service account or API key could be abused. .env is git-ignored, the UI never stores keys, and CI uses repository secrets. High
Single-user, local-only design No authentication, roles or audit log. Not safe on a public host. Bind to localhost by default; document the constraint; add auth before any remote deployment. Low
JSON storage growth Hundreds of full run records accumulate on disk. Runs are small and human-readable; old records can be deleted at any time. A retention policy is on the roadmap. Low

Live fetch is not guaranteed. During the build, the GeM listing endpoint returned HTTP 403 from the development network. Sample mode is the supported fallback, and the run is labelled sample so it can never be mistaken for live data.

19 FAQ

Questions that come up #

Does it bid on tenders automatically?

No. It never logs in, signs, pays an EMD or submits a bid. It produces a ranked shortlist and an eligibility risk list; a human makes the decision and files the bid on GeM.

Is the sample data real?

No. It is a synthetic dataset shaped like real GeM rows, used to demonstrate and test the pipeline without network access. Every run declares source: sample, and sample and live bids are never mixed.

Why did a live scan fail with HTTP 403?

GeM does not publish an official API and may reject automated clients. The app falls back to sample data when GEM_SAMPLE_FALLBACK=true, or you can enable the optional Playwright fallback to make the request from inside a real browser session.

Sheets export says “The caller does not have permission”. Why?

The service account has no access to that spreadsheet. Share the file with the address in client_email from the JSON key, as Editor. Enabling the Sheets API is a separate requirement — both are needed. See Service account and Sheets API.

Do I need paid services to use it?

No. The app runs fully locally with rule-based summaries and CSV output. Groq has a free tier for AI summaries, and Google Sheets requires a free service account but no paid plan.

Where is my data stored?

Settings and run records are plain JSON in data/ (settings.json and runs/). Nothing is sent anywhere except the optional GeM fetch, Groq call and Google Sheets export. Credentials live in .env, which is git-ignored.

Can I change the scoring weights?

Yes. Positive and negative weights live in backend/scoring.py, and risk terms live in backend/constants.py. The UI exposes the threshold (min_score) but not the individual weights, so changes are deliberate and reviewable.

Does it work on macOS or Linux?

Yes. The Python code is cross-platform. Only the activation command and path separators differ; use source .venv/bin/activate and forward slashes.

How many bids can it handle?

The page cap is 50 (five by default). Filtering is linear and cheap; the expensive parts are capped separately by parse_pdf_top_n and summarize_top_n (ten each by default). Increase them only after measuring a run.
